# Audit Follow-up Design

## Goal

Close every actionable item from the September 2026 repository audit while preserving the current single-Dune-root MVP architecture.

## Scope

The work covers:

- ordering concurrent Dune model refreshes;
- migrating legacy auto-generated Dune run configurations;
- defining ownership and customization semantics for managed run configurations;
- making the OCaml fallback lexer safe for incremental relexing and the reported lexical edge cases;
- running blocking toolchain probes on an IntelliJ-managed executor;
- documenting an end-to-end split-mode RPC smoke test;
- preparing version and release-channel metadata for the first `0.1.0` release.

The work does not add multi-root Dune support, expand the S-expression parser without a failing real fixture, publish a release, run CI, or introduce an automated remote-development harness that the project does not currently have.

## Dune Model Refresh Ordering

`DuneRunConfigurationProvisioningService` will assign a monotonically increasing generation to every refresh request. Scheduled work captures its generation, and both background discovery and the EDT application step check that the generation is still current. Disposal invalidates every outstanding generation.

Cancelling a scheduled future remains a debounce optimization, not the correctness mechanism. A completed older `dune describe workspace` result cannot apply after a newer request has been made, even when the older process ignored cancellation or simply took longer.

A focused test will exercise the generation gate by making a newer request before an older result attempts to apply and asserting that only the newer result is accepted.

## Managed Run Configuration Ownership

### Generated baseline

Each plugin-managed configuration will persist the last values generated by the plugin:

- display name;
- Dune-model display name before uniqueness adjustment;
- target;
- working directory.

The generated baseline is ownership metadata. Dune and program arguments are generated as empty values, so any non-empty value is a user customization.

### Detachment

Before reconciliation mutates or removes an existing managed configuration, it compares the current values with the generated baseline. A difference in display name, target, working directory, Dune arguments, or program arguments detaches the configuration by clearing its managed ownership metadata. Detached configurations are treated exactly like manually created configurations from then on.

This makes customization durable: provisioning never overwrites or deletes a configuration after the user has changed it. If the Dune target later changes, the detached configuration remains user-owned and a new managed configuration may be created for the new target.

### Normal managed updates

An unchanged managed configuration continues to follow its Dune model entry. Reconciliation updates its target, working directory, model ID, display name, and generated baseline. Therefore a `public_name` change updates the UI name when the user has not renamed the configuration manually.

### Existing managed configurations

Configurations created by the current ownership implementation have `managedByPlugin` and `modelId`, but no generated baseline. On their first reconciliation:

- an exact current-model match with the expected default name and empty arguments is upgraded in place;
- an exact match with visible customization is detached;
- a stale entry without enough baseline information is preserved by detaching instead of being destructively removed.

### Pre-ownership migration

An unmarked configuration is adopted only when all conservative legacy conditions match:

- `managedByPlugin` is false and `modelId` is empty;
- command matches the desired specification;
- display name is exactly the plugin's default generated name;
- Dune and program arguments are empty;
- target equals the specification's known non-empty legacy target;
- canonical working directory equals the desired working directory.

The adopted configuration is updated in place and receives the current ownership metadata and generated baseline. Any ambiguous or customized configuration remains user-owned.

Integration coverage will include legacy adoption without duplication, detachment after customization, stale detached preservation, and automatic display-name updates for untouched managed configurations.

## OCaml Incremental Lexer

`OCamlLexer` will track the state at the start of each token and the state for the following token, following the existing `DuneLexer` pattern. Multiline comments, normal strings, and quoted strings will be emitted in line-bounded token segments so IntelliJ can restart lexing at an intermediate line with a meaningful state.

Comment state will retain nesting depth and whether scanning is currently inside a string. Comment delimiters appearing inside a string or valid character literal will not change nesting depth. Quoted-string continuation will recover its delimiter from the preceding buffer when incremental lexing starts inside its content; normal full-file lexing records the delimiter directly.

Character literal recognition will consume the complete supported escape form before looking for the closing quote:

- ordinary one-character escapes;
- three-digit decimal escapes such as `\169`;
- two-digit hexadecimal escapes such as `\xA9`;
- three-digit octal escapes such as `\o251`.

Regression tests will cover incremental restarts in each multiline construct, `*)` inside a comment-contained string, and all three numeric character escapes.

## Toolchain Probe Execution

Independent blocking probes will continue to use `CompletableFuture`, but every future will receive `AppExecutorUtil.getAppExecutorService()` explicitly. The executor will be injectable into the internal detection function so a focused test can demonstrate that parallel probes execute on the supplied executor rather than `ForkJoinPool.commonPool`.

The existing OPAM failure short-circuit remains unchanged.

## Split-mode RPC Release Smoke Test

The existing DTO test will remain a narrow serialization-model check and will no longer be presented as end-to-end RPC coverage. A release smoke checklist will require a real split-mode IDE session and verify:

1. frontend settings request a refresh;
2. the backend resolves the project and runs detection;
3. status crosses the Fleet RPC boundary;
4. the frontend `StateFlow` and settings UI receive both success and failure updates;
5. reconnecting or reopening the project re-establishes status delivery;
6. asynchronous semantic highlighting still appears after `ocamllsp` starts.

The README development section will link to this checklist. An automated two-process test is deferred until the repository gains a supported remote-development integration-test harness.

## Release Metadata

The project version becomes `0.1.0`. The changelog will move the current unreleased content into a dated `0.1.0` section and record the audit follow-up changes.

The release workflow will map GitHub release types as follows:

- `released` publishes to the Marketplace default/stable channel;
- `prereleased` publishes to the Marketplace `beta` channel.

The selected channel will be passed into the Gradle publishing configuration. No release is created or published as part of this work. The smoke checklist will note that JetBrains requires the first Marketplace upload to be performed manually.

## Verification Policy

Tests will be written or updated before their corresponding production changes. Per the repository `AGENTS.md`, the agent will not run tests, builds, linters, formatters, Plugin Verifier, IDE instances, CI jobs, or release publication. Final verification is the user's responsibility.
